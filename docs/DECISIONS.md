# Decisions

Lightweight architecture decision records. Newest last. Add an entry whenever a choice
is made that a future session could not derive from the code alone (why, not what).
Product-level choices (stack, hosting, bank access) are summarised in
[plan.md → Decisions](plan.md#decisions); their background is in [tech-stack.md](tech-stack.md)
and [api-access-research.md](api-access-research.md).

Format: **Context** (what forced a choice) · **Decision** · **Consequences**. When a later
decision changes an earlier one, amend the earlier entry in place and say why.

## D-001 · Agent harness ported from Metsävahti (2026-10-23)

- Context: the project is meant to be built mostly by coding-agent sessions, many of them unattended. Metsävahti already has a working harness (course _learn-harness-engineering_ on Claude Code) with a porting guide at its tag `harness-reference`.
- Decision:
  - Port it as the guide prescribes: COPY files stay byte-identical to the reference (a Prettier override in `.prettierrc.json` keeps them in the reference style, so they can be diffed against the tag when re-syncing), ADAPT files get only the guide's § 4 edits, WRITE files follow its skeletons.
  - Deliberate deviations from COPY: `scripts/harness-feature.ts` no longer prints the removed `epic` / `design` fields (two lines), because the feature schema dropped them (no epics or design artboards here). `ticket` is `FIN-NNN` and maps 1:1 to `F-NNN`.
  - Skipped: `import-tickets.ts` and its test (tickets are written alongside `feature_list.json` instead of being parsed from a spec), knip (not used in this repo), design-system lint and the deviations ledger (no design artboards or external spec).
  - Layers are named, not invented: L1 `pnpm check` exists at bootstrap; L2 (`pnpm test:integration`, Vitest + Testcontainers Postgres) is introduced by F-002 and L3 (`pnpm test:e2e`, Playwright) by F-003, each together with its first real tests. Until then the harness runs with L1 only, as the guide allows for projects without integration tests.
  - Unit tests live in `tests/unit/**` (a Vitest project), so the harness tests in `tests/unit/harness/` validate the real `feature_list.json` on every `pnpm check`.
  - The clean-state check forbids added `console.log` in `src/` and allows `console.info/warn/error`, because the repo has no logger; there are no coverage thresholds yet, so that check was removed rather than kept as an always-pass.
  - CI is one job named `Verify`; the features that add L2/L3 add steps to it, so the required status check never changes name.
  - `pnpm typecheck` runs `next typegen` before `tsc`: route types (`LayoutProps`, …) and `next-env.d.ts` are generated and gitignored, and a fresh worktree or CI runner has only committed files (acceptance check 9 caught this).
- Consequences: one manual for every agent (`AGENTS.md`, imported by `CLAUDE.md`); the session loop (read state → one feature → verify → write state) is enforced by scripts and hooks rather than prose; status lives only in `feature_list.json` and only scripts change it.

## D-002 · Driver-run sessions: local loop, auto permissions, PR per feature, opt-in Stop hook (2026-10-23)

- Context: unattended sessions (`pnpm harness:loop`) have nobody to answer questions and run on the host, next to Docker and the dev database.
- Decision (unchanged from the reference's D-008 unless stated):
  - The driver is a local script run on this machine with the existing Claude Code login and host Docker; no CI or cloud runner.
  - Sessions run `claude -p --permission-mode auto --permission-prompts none` with an explicit `--allowedTools` list from `harness.config.json`; the deny list and `guard.sh` still apply; `bypassPermissions` is not used.
  - One worktree and branch `feat/F-NNN` per feature under `../personal-finances-worktrees`, then a PR via `gh`. `harness.config.json` started with `merge: "wait"` (a human merges) and is `"auto"` since 2026-10-23, when `main` got branch protection with the required `Verify` check; switch to `"auto"` once `main` has branch protection with the required `Verify` check, otherwise GitHub would merge before CI.
  - Caps start at the guide's values: 2 attempts, 200 turns, 15 USD, 60 minutes per session; the evaluator 60 turns, 4 USD, 15 minutes. Raise them only after measuring runs (`pnpm harness:report`).
  - Generator/evaluator split: the evaluator is a separate `claude -p` session with the body and tools of `.claude/agents/evaluator.md` (`--append-system-prompt` / `--tools`) and a JSON verdict schema; `--agent` is not used because it ignores `--json-schema`.
  - The Stop hook is inert unless `HARNESS_STOP_GUARD=1` (set by the driver) and blocks at most three times.
  - Features that need real credentials or a person (F-001, F-013, F-023) carry `manual:` steps, so the driver never picks them.
- Consequences: `.harness/` is gitignored; in loop mode `guard.sh` additionally blocks `pnpm db:up/down`, `git push`, leaving the branch, worktree commands and writes outside the worktree; one feature runs at a time; `gh` must be installed and logged in for PRs.

## D-003 · pnpm instead of npm, and `pnpm add` allowed unattended (2026-10-23)

- Context: the harness scripts, hooks, skills and driver call `pnpm`, and every feature installs dependencies in a fresh worktree, which is only fast with pnpm's shared store. The repo started on npm.
- Decision:
  - Switch to pnpm: `pnpm import` converted the lockfile (same versions); `packageManager` pins **pnpm 10.15.0**, run through corepack. pnpm 12 was tried first, but it creates directory symlinks, which fail on Windows without admin rights or developer mode; pnpm 10 uses junctions. Build-script approvals moved from npm's `allowScripts` to `pnpm.onlyBuiltDependencies`.
  - `"type": "module"` in `package.json`, because the harness scripts are ESM.
  - `Bash(pnpm add *)` is in the unattended `allowedTools`: features must add the dependencies their tickets name (Testcontainers, Playwright, iron-session, jose, Recharts, …). `guard.sh` still blocks npm, yarn and npx, and the lockfile can only change through pnpm.
- Consequences: the Docker images install with `pnpm install --frozen-lockfile` via corepack; a dependency an unattended session adds is visible in the PR diff (`package.json`, `pnpm-lock.yaml`) and reviewed by the evaluator and the human merging the PR.

## D-004 · The harness is the shared package and Claude Code plugin, not a copy (2026-10-23)

- Context: D-001 ported the harness by copying files from Metsävahti's `harness-reference` tag. The copies drifted at once: Metsävahti fixed the loop's wait on a failed CI check after the tag, Ideaforge fixed the guard's command matching, and neither fix reached this repository without porting it by hand.
- Decision: the harness now comes from `Eemelinen/harness`, pinned to one git tag twice. The package is `@eemelinen/harness` (`devDependencies`, `github:Eemelinen/harness#vX.Y.Z`; the `harness` CLI behind `pnpm harness:*`). The Claude Code plugin is `harness@eemelinen-harness` (`.claude/settings.json` → `extraKnownMarketplaces` with `ref`, `enabledPlugins`; skills `/harness:*`, agent `harness:evaluator`, the hooks). Everything that was a project edit of a copied file is configuration in `harness.config.json`: the `FIN-NNN` ticket format, the guard rules for `next-env.d.ts`, `drizzle/` and `.env*`, the `.only`/`.skip` check over `tests` and `src`, the `console.log` check, the marker block, the Docker services and the session-start lines. The ticket and deviation instructions moved into `docs/harness/generator-notes.md`. `pnpm check` runs `pnpm harness:check` instead of the copied unit tests, and `./init.sh` runs `pnpm harness:doctor`. Driver sessions load the plugin from the installed package (`--plugin-dir`) and stop when it is missing. This amends D-001 and D-002.
- Consequences: the copied scripts, hooks, skills, prompts, evaluator and harness tests are gone, along with the Prettier override that kept them in the reference style. Harness fixes arrive by bumping both pins (`docs/harness/README.md`). Skill names gained the `harness:` prefix. Interactive sessions need the folder trusted once for the marketplace and the permissions to apply.

## D-005 · Core schema types: `date` for calendar days, `bigint` read as `number`, open-text providers (2026-10-23)

- Context: F-002 creates the first schema. FIN-002 asks for `timestamptz` everywhere, `bigint` minor units with a `char(3)` currency and an `account_type` enum, and leaves the rest open.
- Decision:
  - Points in time are `timestamptz`; calendar days (`booking_date`, `value_date`, the snapshot `date`) are `date` (read as `YYYY-MM-DD` strings). A bank's booking day is not an instant, and a timestamp at UTC midnight would show as the previous day in another zone.
  - Money is `bigint` minor units read as JS `number` (exact to 2^53 cents), not `bigint`, so values serialise to JSON and work with arithmetic without conversions.
  - `provider` columns are open `text` (new providers need no migration); closed sets (account type, statuses, category source and kind, rule match field and type) are Postgres enums. Ids are `uuid` (`gen_random_uuid()`).
  - Dedupe identity is `dedupeHash()` (`src/server/dedupe-hash.ts`): SHA-256 over the normalised booking date (`YYYY-MM-DD`, ISO timestamp or `d.m.yyyy`), the integer amount and NFKC-normalised, lower-cased, whitespace-collapsed counterparty and description.
  - L2 runs one Testcontainers `postgres:18-alpine` per test file, migrated by the same `applyMigrations()` the `migrate` service uses.
- Consequences: deviations are listed in FIN-002's Notes. Amounts beyond 2^53 minor units would need `mode: "bigint"`; F-019 decides quantities for crypto separately.

## D-006 · L3: Playwright against the standalone build with its own Testcontainers Postgres; shadcn/ui Nova (2026-10-23)

- Context: F-003 introduces the L3 layer and the app shell. FIN-003 asks for a `webServer` that builds and serves the app on a fixed test port, and leaves the e2e database open (Testcontainers or a compose `db_test` service). Loop sessions must not run Docker Compose, and the machine already runs other projects' containers.
- Decision:
  - The e2e database is **Testcontainers**, not a compose service: `tests/e2e/support/server.ts` (Playwright's `webServer`) starts `postgres:18-alpine` with the same `startTestDatabase()` L2 uses, so it is migrated by the app's own runner, then runs `pnpm build` and serves `.next/standalone/server.js` (what the Docker image runs, static assets copied in the same way) on `127.0.0.1:3100` (`E2E_PORT`). Playwright waits for `/api/health`, which only answers 200 once the app reaches that database. Nothing touches the dev database, and the container dies with the process (SIGTERM, else Ryuk).
  - `reuseExistingServer: false`: the fixed port must never silently test some other server. `E2E_SKIP_BUILD=1` reuses an existing build (CI builds once, before L3).
  - Chromium only, `retries: 0`, `forbidOnly`. Desktop and mobile widths are `test.use` viewports inside one spec rather than two projects, so each assertion states which layout it checks.
  - `@playwright/test` is pinned exactly to **1.63.0**, the version whose Chromium revision (1243) is already installed on the loop machine; a newer release needs a new browser download, which an unattended session must not do to the host. Bump it together with `pnpm exec playwright install chromium`; `./init.sh` warns when the revision is missing.
  - shadcn/ui was initialised with the CLI (`-b radix -p nova`): Radix primitives, `lucide-react`, the `cn` package, theme variables in `globals.css`. The CLI added `shadcn` itself as a runtime dependency for its `tailwind.css`; it is a devDependency here, because the CSS is resolved at build time.
  - Pages live in the `(app)` route group whose layout renders the shell; a page without it (F-004's login) goes outside the group. The active nav link uses `usePathname()` inside `<Suspense>` with an unhighlighted fallback, so a future dynamic route cannot fail the Cache Components prerender.
- Consequences: L3 needs Docker and the Playwright Chromium. The fixed port keeps loop runs sequential (already the case for Compose). Next 16 keeps visited pages mounted but hidden, so non-role e2e locators need `.filter({ visible: true })`.

## D-007 · Single-user login: base64url-encoded hash, stateless iron-session, daily re-issue, global backoff (2026-10-23)

- Context: F-004 adds the login. FIN-004 names argon2, `AUTH_PASSWORD_HASH`, iron-session with `SESSION_SECRET`, a 30-day sliding expiry, `src/proxy.ts` plus a data access layer check, and an in-memory backoff after 5 failures; the details are open.
- Decision:
  - `AUTH_PASSWORD_HASH` holds the argon2id PHC string **base64url-encoded** (`pnpm auth:hash` prints it). The Next.js `.env` loader expands `$name` even in single or double quotes, so a raw `$argon2id$v=19$…` would arrive mangled, and Docker Compose escapes `$` differently (`$$`) from Next (`\$`). A raw PHC string is still accepted when the variable is set without a `.env` file. Hashing uses `@node-rs/argon2` defaults (argon2id, m=19456 KiB, t=2, p=1).
  - The login secrets have their own schema, `getAuthEnv()` in `src/server/env.ts`, which only the app calls; the worker and the migrate job do not get them (Compose sets them on `app` only). `SESSION_SECRET` must be at least 32 characters (iron-session's minimum).
  - The session is stateless: the cookie `pf_session` seals only `{ issuedAt }`. It is valid for 30 days from `issuedAt` (checked explicitly and by the seal's own TTL). "Sliding" is implemented by the proxy re-issuing the cookie once the session is a day old, rather than on every request, so prefetches do not rewrite the cookie constantly. Logout deletes the cookie; it cannot revoke a copied cookie, which rotating `SESSION_SECRET` does.
  - `secure` is set when `NODE_ENV=production`. Browsers accept secure cookies on `http://localhost` and `127.0.0.1` (L3 runs that way), and Compose binds the app to `127.0.0.1`, so remote access needs a TLS proxy anyway.
  - Backoff: after 5 consecutive failures each attempt is refused until 1 s, 2 s, 4 s, … (cap 15 min) after the last failure; a success resets it. It is global, not per IP, because there is one account and client IPs behind a proxy are spoofable; the trade-off is that someone who keeps sending a wrong password whenever the window opens can keep the owner locked out. That is accepted because the app is bound to `127.0.0.1` (only someone already on the machine or behind the owner's own proxy can reach it); restarting the app clears the counter. Attempts are serialised (`createLoginChecker()` in `src/server/auth/login.ts`) so parallel requests cannot all pass before earlier failures are counted, and a refused attempt neither runs argon2 nor counts as a failure.
  - The proxy answers 401 JSON for `/api/*` without a session and redirects every other path to `/login`; `/login` with a valid session redirects to `/`. `/api/health` skips the session check entirely, so it still reports the database state when the login secrets are missing; every other path fails fast on them (500). The decision is the pure `accessDecision()` (`src/lib/auth/routes.ts`), unit-tested with the re-issue (`refreshSession()`). After login the app always opens `/` (no return-to parameter, so no open-redirect check is needed yet).
  - The proxy skips the daily re-issue on Server Action calls (`isServerActionRequest()`: a POST with `Next-Action`), because the action may change the cookie in the same response; logout must always end with the cookie gone. Amended by D-021: that was not enough, a concurrent prefetch could still re-issue the cookie after logout, so the proxy now re-issues on page loads only (`mayReissueSession()` replaces `isServerActionRequest()`). `getSession()` awaits `io()` before reading the clock (the guide's alternative, `'use cache: private'`, would cache the session check in the browser, which a stateless logout cannot invalidate).
  - L3 logs in once in a Playwright `setup` project and stores the browser state; `tests/e2e/support/credentials.ts` holds the test-only password and secret, and the e2e server hashes the password at startup.
- Consequences: a new Route Handler, Server Action or data-reading component must call `verifySession()` itself (architecture → Security). The backoff resets when the app restarts. `pnpm test:e2e <spec>` always runs the `setup` project first. L3 fails when the app server prints an error line (`tests/e2e/support/server-errors.ts`, Playwright global teardown), so a Cache Components or action error that leaves the page intact still breaks the run.

## D-008 · Provider contract: date-string ranges, decrypted connection, fake registered only on `BANK_PROVIDER=fake`, `v1:` AES-GCM format (2026-10-23)

- Context: F-005 finalises the `FinancialProvider` sketch in the architecture doc, adds the typed errors, the registry, the fake provider and the encryption of stored session ids. FIN-005 leaves the shapes, the switch and the key format open.
- Decision:
  - DTOs mirror the table columns (integer minor units + currency, `YYYY-MM-DD` calendar days, provider ids as `ref`). The transaction range is inclusive calendar days `{ from, to? }` as strings rather than the sketch's `Date`s (amended by D-010: `from` is optional and listings are paged), because the bank APIs and the `date` columns both work in days and a `Date` would bring a time zone into a day boundary. Providers receive `ProviderConnection { sessionRef }` with the session id already decrypted, so they never see `ENCRYPTION_KEY` or the database.
  - Typed errors carry a `kind` and the `providerId`; `providerErrorFromStatus()` is the single HTTP mapping (401/403 auth, 429 rate limit with `Retry-After`, 408/5xx unavailable, everything else a bug that is not caught). `getHoldings()` is optional with a provisional `{ symbol, quantity: string }` DTO that F-019 finalises (amended: F-019 finalised it with the asset's identifiers, class, currency and the quantity's date, D-016).
  - `BANK_PROVIDER` (`enable_banking` default, or `fake`) is in the main env schema because app and worker both need it. The fake is registered only when it is selected, so a real installation never answers a `provider = 'fake'` row with fake data. The fake derives each day's transactions from a SHA-256 of account ref and day (no stored state, no seed), so separate processes (the e2e app server and the test runner) agree without sharing memory; only "today" reads the clock (injectable), as a UTC date, because the fake reads no environment (`APP_TIMEZONE`). Failure modes are selected by special session refs (`fake:expired`, …) for the same reason.
  - `ENCRYPTION_KEY` is 32 random bytes, base64, in its own schema (`getEncryptionEnv()`), like the login secrets, so the migrate job and `/api/health` keep working without it. Ciphertext is `v1:<iv>:<ciphertext>:<tag>` in base64url, with the version as GCM additional data, a 16-byte tag enforced on decryption and only canonical base64url accepted; a later `v2` (new key or format) can sit next to `v1` values.
- Consequences: F-006 registers Enable Banking in `defaultProviders()` and maps its HTTP failures with `providerErrorFromStatus()`; F-007 stores `encryptSecret(sessionId)` in `connections.session_ref` and needs `ENCRYPTION_KEY` passed to the Compose `app` and `worker` services (not done yet: nothing reads it at runtime). Key rotation is not built. L3 runs with `BANK_PROVIDER=fake` and a test-only key from `tests/e2e/support/credentials.ts`.

## D-009 · Balance sync: fetch first, write in one transaction; provider errors are results; default display balance order (2026-10-23)

- Context: F-008 adds `syncBalances(connectionId)`. FIN-008 asks for a preferred display balance type per bank "from F-001 findings", which do not exist yet (F-001 is human-only), and leaves open how failures, archived accounts and the snapshot day are handled.
- Decision:
  - All provider calls happen before any write, and the account and snapshot changes, the run's counts and `last_synced_at` are written in one transaction, so a failure halfway never leaves half a sync. The `sync_runs` row is inserted first, outside it, so a failure is recorded even when the transaction rolls back.
  - `ProviderError`s are expected states, not bugs: they are recorded on the run and returned with their `kind` (and `retryAfterMs`), so a scheduled sync of many connections (F-010) needs no try/catch per connection for them. Only `auth_expired` changes the connection (`expired`); a missing session counts as one. A non-`active` connection is not synced but still gets a failed run, so "Sync now" on it leaves a visible log entry. Everything else is rethrown after failing the run.
  - A snapshot's day is the date the provider reports for that balance (the fake: `CLBD` yesterday, `ITAV` today), not the sync's local day, so a closing balance is never filed under the wrong day. Unchanged snapshots are not rewritten (`ON CONFLICT … DO UPDATE … WHERE … IS DISTINCT FROM`), so `updated_count` means changed.
  - Display balance: default order `ITAV`, `CLAV`, `ITBD`, `CLBD`, `XPCD`, `OPAV`, `OPBD` (available before booked, interim before closing), then the latest day of that type; per-bank overrides keyed by `institutions.provider_ref`, empty for now. All types are stored, so a later change of preference needs no re-sync.
- Consequences: F-001 / F-006 add per-bank entries to `BALANCE_TYPE_PREFERENCE_BY_INSTITUTION` if a bank's preferred type differs. F-009 can extend the same run or add its own (it added its own, D-010); F-010 must hold the advisory lock around `syncBalances()` (accounts have no unique `(connection_id, provider_account_ref)` constraint) and decide what to log for a failed result. Dashboard queries (F-016/F-018) use `pickDisplayBalance()`.

## D-010 · Transaction sync: own run, per-account watermark and commit, paged contract, pending matched by amount (2026-10-23)

- Context: F-009 adds `syncTransactions(connectionId)`. FIN-009 asks for an incremental sync "from `last_synced_at` minus a 7-day overlap", pagination, pending-to-booked replacement and preserved manual "category or note edits", but `connections.last_synced_at` is also set by `syncBalances()`, the provider contract returned one unpaged array with a mandatory `from`, and `transactions` had no note column. Two identical same-day transactions without a ref collided on `dedupe_hash` (FIN-002 Notes).
- Decision:
  - `syncTransactions()` writes its own `sync_runs` row (shared bookkeeping in `src/server/sync/runs.ts`, which `syncBalances()` now uses too) and syncs the accounts the last balance sync stored. F-010 calls `syncBalances()` first, then `syncTransactions()`.
  - The watermark is per account: new column `accounts.transactions_synced_at`, set when that account's transactions were written. The connection-wide `last_synced_at` would be advanced by a balance sync while transactions keep failing (a gap after 7 days), and would give an account added later only 7 days of history. `last_synced_at` is still set on success, as "last successful sync of any kind". The window is the account's last sync day in `APP_TIMEZONE` minus 7 days, extended back to its oldest stored pending transaction so a pending one that went away is seen as gone.
  - Backfill asks without `from`: `TransactionRange.from` is now optional and means "the oldest day the provider can return", because only the provider knows its history limit. `getTransactions()` takes a `continuationKey` and returns `{ transactions, continuationKey }` (the Enable Banking shape); `fetchAllTransactions()` follows the pages and treats a repeated key or more than 1000 pages as a bug. The fake pages too (100 per page by default), so every test and L3 go through paging.
  - Each account is fetched completely and written in its own database transaction, so a rate limit on the second account keeps the first (unlike the all-or-nothing balance sync: PSD2 allows only a few unattended calls per account per day, so re-fetching finished accounts would waste them). A failure on a later page of one account writes nothing for it.
  - Matching order: ref, then hash, then a stored pending transaction with the same amount and currency at most 7 days away (same counterparty first, nearest day next). Banks often give a pending card payment no id or another id, day and text than its booked version, so ref and hash alone would insert a duplicate and lose edits made on the pending one. Matches are updated in place; the sync never writes `category_id`, `category_source`, `note` or `transfer_group_id`. Unmatched stored pending rows are deleted (with any edits on them); booked rows are never deleted. The hash fallback also applies when both refs are non-null and differ: the stored row takes the new ref, on the assumption that the bank reissued the id (a genuinely different transaction with identical content gets its own occurrence number instead).
  - `transactions.note` (nullable text) is added now, so "never overwrites note edits" is real and tested; F-015 adds the UI. Identical transactions in one listing get an occurrence number in their hash (`dedupeHash({ …, occurrence })`; the first keeps the old hash), numbered by ref and then listing order, so re-syncs number them the same way. The CSV importer (F-012) should number its rows the same way.
  - The categorisation hook is an option (`categorize(tx, insertedIds)`), called in the account's database transaction after inserts; the default does nothing until F-014. (D-012: it now receives inserted and updated ids, and the rule engine is the default.)
- Consequences: F-006 implements the paged contract (Enable Banking `continuation_key`) and maps a missing `from` to the bank's maximum history. F-010 runs `syncBalances()` then `syncTransactions()` under the advisory lock and decides what to log for a failed result (it may carry counts of the accounts done). F-014 passes its rule engine as `categorize` (or makes it the default). F-015 edits `note`, `category_id` and `category_source`; the sync leaves them alone. A pending transaction with a manual edit that the bank drops (cancelled authorisation) is deleted with its edit. Known gaps (F-009 review): when a ref-matched row must move to the next free occurrence hash, only loaded rows are checked, so a stored row with that exact hash that shares no ref or hash with the listing would fail the account's sync on the unique key (needs identical same-day transactions with changing refs); and the window reaches back to the oldest stored pending transaction even past a bank's history limit, which F-006 should clamp or map. A failed run records the counts of the accounts already written, also when it failed on a bug.

## D-011 · CSV import: own parser, header-based bank layouts, insert-only through the sync's identity (2026-10-23)

- Context: F-012 adds `/import` for Nordea and S-Pankki netbank CSV exports and a generic CSV. FIN-012 asks for "the same upsert and dedupe path as API sync" and no duplicates between overlapping imports and API data, but the real export layouts are not documented anywhere the session could reach, no real export may be committed, the architecture sketched the importer as a `providers/csv/` provider, and the tech stack listed papaparse as the candidate parser.
- Decision:
  - The importer is not a `FinancialProvider`: an upload is pushed by the user, has no session, no pages and no balances, so it lives in `src/server/csv/` (`parse.ts`, `values.ts`, `bank-csv.ts`, `import-csv.ts`). `institutions.provider` is `csv` for the manual accounts it creates.
  - Own RFC 4180 reader (about 100 lines, quoted fields with `""` and line breaks, each record keeps its file line for the row numbers in the summary) instead of papaparse: no new dependency, and the line numbers, delimiter detection and Windows-1252 decoding are under test either way.
  - Decoding: valid UTF-8 (BOM dropped), otherwise Windows-1252. Delimiter: the one under which a known bank header row is found, otherwise the one that gives most rows the same column count.
  - The bank layouts are recognised by their Finnish header names, not column positions, so column order, preamble lines and the delimiter may vary: Nordea = `Kirjauspäivä` + `Määrä` (counterparty `Saaja/Maksaja`, or `Maksunsaaja` for money out / `Maksaja` for money in, else `Nimi`; text `Viesti`, `Otsikko`, else `Tapahtuma`; optional `Arvopäivä`, `Valuutta`), S-Pankki = `Kirjauspäivä` + `Summa` (counterparty `Saajan nimi` for money out / `Maksaja` for money in; text `Viesti`, else `Tapahtumalaji`; value date `Maksupäivä`). These names are the best available reading of the netbank exports and are unverified against a real file; the generic mapping is the fallback when a bank changes its layout. A Nordea `Varaus` (reservation) row is reported as an error, not imported.
  - Amounts: decimal comma or point, space / no-break space / point / comma / apostrophe groups, `+`, `-`, `−` or a trailing `-`, two decimals at most (EUR); a lone separator followed by exactly three digits groups thousands. Dates: `d.m.yyyy`, ISO `yyyy-mm-dd`, `yyyy/mm/dd`; no ambiguous `dd/mm` vs `mm/dd`.
  - Writing: rows become booked `ProviderTransaction`s without a ref and go through the sync's `identifyTransactions()`, so otherwise identical rows get the same occurrence numbers as in a bank listing and hash like the bank sync's rows (FIN-002 Notes, D-010). They are inserted with `ON CONFLICT (account_id, dedupe_hash) DO NOTHING`; conflicts are the "skipped as duplicates". An import never updates, books or deletes a stored row: a CSV has no refs and no pending state, so it cannot improve a synced row, and the next bank sync adopts imported rows by hash (they get the bank's ref, keep their id). The `categorize` hook runs on the inserted ids, as in the sync.
  - Target: any non-archived account (bank-synced or manual) or a new manual account (EUR, `checking` or `savings`) under one `csv` institution per format (`provider_ref` = `nordea`, `s-pankki`, `generic`; country `FI`). A new account is created in the same database transaction as its rows (`importCsvIntoNewAccount()`), and not at all when no row is importable, so a failed import leaves no empty account. Rows with a `Valuutta` other than the account's currency are errors; the preview does not know the target account, so it shows them as readable and only the import summary lists them. Imports write no `sync_runs` row (it requires a connection); the summary is returned to the page only.
  - UI: two Server Actions (preview, import) that both receive the file, so the server keeps no upload state; files up to 4 MB (`serverActions.bodySizeLimit` 5 MB). The preview shows the first 200 rows. `/import` is linked from the Transactions and Connections empty states, not the main navigation.
- Consequences: F-001 / F-006 should compare an anonymised real export and the Enable Banking texts with these layouts: if the API's counterparty or remittance text differs from the CSV's, an overlap between a sync and an import is not detected by hash and inserts duplicates (the tests prove the path with identical texts only). F-010's advisory lock should also cover imports into a bank-synced account; a sync that runs at the same moment as an import into the same account can fail on the unique key and is retried by the next sync. F-014's rule engine plugs into `importCsvRows()` as `categorize` too. Nordnet CSV (F-020) can reuse `parse.ts` and `values.ts`.

## D-012 · Categorization: seeded once into an empty table, rules then transfers in the write transaction, rule categories guard transfer pairing (2026-10-23)

- Context: F-014 adds the rule engine and own-transfer detection. FIN-014 asks for seeded two-level categories and Finnish merchant rules, rules on counterparty or description (contains, equals, regex) with an optional amount sign or range, priority order with the first match winning, manual categories never overwritten, a re-apply over all non-manual transactions, and transfer pairs (same absolute amount between own accounts within ±3 days, or to an own IBAN) with the Transfers category and a shared `transfer_group_id`. `category_rules` had no amount columns, transactions carry no counterparty IBAN, and the F-009 hook received inserted ids only.
- Decision:
  - Schema: `category_rules.amount_sign` (`rule_amount_sign` enum `debit` / `credit`, null = either) and `amount_min_minor` / `amount_max_minor` (inclusive bounds on the absolute amount, null = open), migration `0002_categorization_rules.sql`. Sign plus an absolute range expresses every signed range and reads as the user thinks ("debits between 10 and 50 €").
  - Seeding is code, not a data migration (`seedDefaults()`, run by `src/server/db/migrate.ts` after the migrations, under an advisory lock): it writes only into an empty `categories` table, so categories and rules the user deletes do not return on the next start. New default rules in a later version therefore do not reach existing installations; that needs a versioned seed if it is ever wanted.
  - Matching: `contains` / `equals` are case-insensitive with whitespace collapsed; `regex` is a JavaScript regex with the `i` flag; an invalid pattern never matches (F-015 validates on save). Ties in `priority` go to the older rule, then the id. Seeded merchant rules match the counterparty; short or ambiguous names (`VR`, `HSL`, `Sale`, `Alko`, `DNA`, …) are word-bounded regexes. Salary, rent, Kela and tax refunds match with a sign.
  - No match means no category and `category_source = 'none'`; the seeded Uncategorized category is for manual picks and reports, not assigned by the engine. A changed or deleted rule therefore also clears the categories it gave on re-apply.
  - Kinds: `Income` is `income`; `Transfers` and `Savings & investments` are `transfer` (moving money to savings or a broker is not consumption); the rest `expense`.
  - The hook (`categorizeTransactions`) is the default `categorize` of `syncTransactions()` and the CSV import, and the sync now passes the ids of inserted and updated transactions (a deviation from the F-009 "inserted ids" hook): a pending transaction booked in place is re-categorised and can then pair.
  - Transfers: only booked, non-manual transactions in no group (or alone in one) take part. "Own IBAN" is read from the transaction texts (an own account's IBAN contained in the counterparty or description, spaces and case ignored), since there is no counterparty IBAN column; such a leg pairs only with a leg on that account, and without one becomes a one-sided transfer whose group a later leg joins. To keep equal amounts that are not transfers apart, both legs must be on different accounts, and a leg that a rule put into any category other than Transfers pairs only when an IBAN names one of the accounts (so a Nordnet payment, Savings & investments by rule, does not pair with an unrelated equal credit; F-020 makes Nordnet an own account) (a refinement of the ticket's amount-and-date rule, recorded in FIN-014 Notes). Matching is nearest-day-first over all candidate pairs (the pool indexed by amount and currency), each leg used once. Linked legs get the top-level Transfers category (created on demand if missing) with source `rule`; rules skip grouped transactions, so re-apply keeps transfers.
- Consequences: F-015 sets `category_source = 'manual'` on inline edits and on an unlinked transfer (otherwise re-apply links it again), should validate regexes, and calls `reapplyRules()` for "apply to past transactions". F-016+ leave category kind `transfer` out of spending and income and show a null category as Uncategorized. The e2e server applies migrations without seeding, so F-015's e2e must seed (or create) the categories it needs. Two writers pairing at the same moment (an import during a sync) could each link the same free leg; F-010's advisory lock should cover imports too. A pending leg is never paired, so a transfer shows up as a pair from the day both legs are booked.

## D-015 · Balance history: snapshot-anchored backward reconstruction, EUR non-archived accounts, ranges ending today, shared date module (2026-10-24)

- Context: F-018 adds `/reports/balances`. FIN-018 asks for a net-worth line and a stacked per-account area chart over 3 months, 6 months, 1 year or all, the last known balance carried over days without a sync, history before the first sync reconstructed from transactions and marked estimated, and a per-account tooltip. It leaves open where a range starts, which accounts count, what the reconstruction starts from, which transactions it subtracts, how far back it goes, and how "estimated" is shown.
- Decision:
  - Ranges (`src/server/reports/balance-series.ts`): `?range=3m|6m|1y|all`, default 3 months, anything else is the default. A month range ends today (`APP_TIMEZONE`) and starts the day after the same day that many months earlier (day of month clamped), so a year is 365 or 366 days; `all` starts at the earliest first snapshot or first transaction of the drawn accounts. Days, not whole months as in the spending periods (D-014): a balance is a point in time, and a line ending today is what the dashboard's totals show.
  - Accounts: non-archived EUR accounts, as the dashboard's net worth (D-013), ordered by bank and name, so colours follow the account, not its rank. An account without any snapshot (CSV imports only, D-011) has no balance to start from and is left out; the page counts the omitted ones (and other currencies) below the table.
  - A day's balance from the first snapshot on is `balanceOn()` (D-013: the display balance of the latest snapshot day, carried over). Before it, back to the account's first transaction, it is the first snapshot day's display balance minus the transactions booked after that day up to and including the snapshot day (a closing balance includes its own day), marked estimated. Counted: all of the account's EUR transactions, booked and pending (as D-014), transfers included, since they moved money. Before the first transaction the balance is unknown (no point, a gap in the line), not assumed to be the opening balance.
  - Net worth is the daily sum of the known balances, estimated when any part is, and partial on a day some drawn account has no balance yet (the sum covers only the others); on a day no account has a balance it is unknown. The net-worth line is solid where complete and synced, dashed where estimated and grey (muted) where partial, with each style change bridged so the line has no gaps; both charts shade each run of estimated days ("Estimated"); in the stacked areas an unknown balance is a gap, not zero; the tooltip lists each account's balance with "(est.)" and the net worth with "(partial)"; the accounts table shows the range's first day and today with the change.   - Colours: eight categorical series colours as CSS variables (`--series-1…8`, light and dark steps, checked for colour-vision separation); a ninth account and later fold into one Other series rather than generating hues. Three light steps fall below 3:1 contrast, so the legend, tooltip and table carry the names and values.
  - `addDays()` / `localDate()` (and `dayNumber()`) moved from `src/server/sync/transaction-merge.ts` to `src/server/dates.ts`, as D-013 asked once F-018 reused them.
  - L3: `balance-history.spec.ts` runs in the shared `chromium` project. It seeds its own bank, account, snapshots and transactions and asserts only that account's row and the day counts, so other specs' accounts do not affect it.
- Known limits: when the first snapshot is an available balance (`ITAV`) and a pending transaction before it has since been booked on another day, or the anchor is a booked balance (`CLBD`) while pending transactions are subtracted, an estimate can be off by those pending amounts. An account added later still raises the drawn net worth on its first known day; the grey partial style and the like-for-like change say so, but the line's step remains. The `all` range draws one point per day (a few thousand points for years of history).
- Consequences: Nordnet and Kraken holdings (F-020+) become further accounts in the stack once they have snapshots; non-EUR accounts need exchange rates first, as in D-013 and D-014.

## D-016 · Investment data model: numeric(38, 18) decimals, decimal unit prices in minor units, holdings as quantity snapshots, ECB rates per EUR (2026-10-24)

- Context: F-019 adds the investment tables and a valuation function. FIN-019 asks for assets (symbol, ISIN or CoinGecko id, asset class, currency), holdings with quantity snapshots, investment transactions (buy, sell, dividend, fee, transfer), daily prices and ECB FX rates, with quantities as `numeric` and money in minor units, a valuation as Σ quantity × price × FX with a missing price falling back to the last known one, and an optional `getHoldings()`. It leaves open the decimal precision, how a unit price below a cent fits "minor units", which way a rate points, what a holding row means over time, how rounding works and what happens without any price.
- Decision:
  - Quantities, unit prices and FX rates are `numeric(38, 18)`: 18 decimals (ERC-20 tokens use 18), 20 integer digits. Drizzle reads them as strings; arithmetic is BigInt fixed-point (`src/server/investments/decimal.ts`, `parseDecimal()` rejects more than 18 significant decimals and exponent notation), never a JS number. `tsconfig.json` targets ES2017, so the code uses `BigInt(…)` instead of `0n` literals rather than raising the target for one module.
  - Money stays in minor units: cash flows (`investment_transactions.amount_minor`) are `bigint`, as everywhere (AGENTS.md). A unit price is a rate per unit, not an amount that gets summed, so `prices.price_minor` is minor units of the price's currency as a `numeric(38, 18)` decimal (a 0.12345-cent coin, a fund share quoted to four decimals). Refinement of the integer-minor-units rule for unit prices only, recorded in FIN-019 Notes.
  - `holdings` are quantity snapshots: one row per account, asset and day; a quantity holds until the account's next snapshot of that asset, and 0 means sold out (rows are never deleted to sell). F-020 derives them from transactions, F-021 stores `getHoldings()` results; valuation reads only snapshots, never transactions. Quantities are ≥ 0 (no short positions).
  - `investment_transactions.quantity` is the signed change in units held and `amount_minor` the signed cash effect, so a transfer in or out needs no extra direction column; `asset_id` is null for cash-only rows. They dedupe like bank transactions (`provider_txn_ref`, `dedupe_hash` per account); the hash's inputs are F-020's choice.
  - Assets are unique by ISIN and by CoinGecko id when present; symbols are not unique (one ticker on several exchanges). `asset_class`: `stock`, `etf`, `fund`, `crypto`, `other` (FIN-022's allocation folds stocks and ETFs; cash comes from bank accounts and `balance_snapshots`, so there is no cash class). `currency` is the quote currency; each price row carries its own currency, which the conversion uses.
  - `fx_rates` keep the ECB convention, units of the currency per 1 EUR, one row per currency and working day (EUR has no row; its rate is 1). EUR value = q × p × 10^2 / (10^e(currency) × rate) with minor-unit digits from `Intl` (`currencyExponent()`: JPY 0, KWD 3).
  - Valuation (`valueHoldings()`, `getAccountValuation()`): per asset the latest holding snapshot, price and rate on or before the day (so weekends, holidays and a failed fetch carry the last known value; there is no age limit); the exact product is rounded once per position, half away from zero, and the total is the sum of the rounded positions, so a holdings table adds up. An asset with no price, or a currency with no rate, on or before the day is listed with `missing` and `valueMinor: null`, left out of the total, and the result is `complete: false`, rather than failing or counting it as 0 silently. Holdings only: the account's cash balance is added by the net-worth feature (F-022).
  - `ProviderHolding` (D-008's provisional DTO) is final: `symbol`, `name`, `isin`, `coingeckoId`, `assetClass`, `currency`, `quantity` (decimal string) and `date`, so a sync can match or create the asset (ISIN, else CoinGecko id, else symbol and currency) and write a snapshot. `getHoldings()` stays optional; Kraken implements it since F-021 (D-018), which also refines the symbol fallback of the asset match.
- Known limits: rounding per position means the total can differ by a cent per position from rounding the exact sum; a long-stale price is used without warning except through the returned `price.date`; `numeric(38, 18)` caps quantities and prices at 10^20. Minor units here follow the currency's own digits (`currencyExponent()`: a JPY price is in yen), while `formatMoney()` in `src/lib/format.ts` still divides every currency by 100; the two agree for EUR and other 2-digit currencies only. `fx_rates` is unique on `(date, currency)`, which a latest-rate-per-currency lookup does not use as well as `(currency, date)` would; fine at today's volumes.
- Consequences: F-020 writes `assets`, `investment_transactions`, derived `holdings`, `prices` and `fx_rates` (upserting on the unique keys) and shows positions from `getAccountValuation()`; F-021 maps `BalanceEx` to `ProviderHolding` and, since a quantity holds until the next snapshot, writes an explicit `0` snapshot when an asset drops out of `getHoldings()` (else its last quantity keeps being valued); F-022 sums account valuations per day (one query per account and day today; a range query may be needed for long histories) and feeds them into the balance history (D-015).

## D-017 · Nordnet import and stock prices: header-driven reader, one brokerage account per portfolio, holdings re-derived, Twelve Data behind a client-side limiter, trade prices as fallback (2026-10-24)

- Context: F-020 imports Nordnet transaction exports, derives holdings, fetches daily closing prices and ECB rates within a free-tier limit, lists holdings on `/investments` and counts them in net worth. Nordnet does not document the export, and nobody could confirm a real layout during the session (the only public samples are user posts: tab or `;` delimited, UTF-16 or UTF-8, decimal commas, ISO or `d.m.yyyy` dates, repeated `Valuutta` columns, the security name in `Arvopaperi`). The ticket leaves open which price API, how a portfolio maps to an account, how re-imports dedupe, what each Nordnet type becomes and what "included in net worth" means before F-022.
- Decision:
  - Reader (`src/server/investments/nordnet-csv.ts`): columns found by header name in Finnish, English or Swedish; UTF-16 (byte order mark), UTF-8 or Windows-1252 (`decodeCsv()` gained UTF-16); tab, `;` or `,`; preamble lines above the header allowed. A `Valuutta` column belongs to the value column before it: the amount's currency is the one after `Summa`, the price's the one after `Kurssi`, else after `Kokonaiskulut`, else the amount's. Numbers use a decimal comma (`3,235` is 3.235, not 3235 as the bank reader would group it); with both a comma and a point the last one is the decimal separator (`1,234.56` from an English export). An asset's quote currency comes from a buy or sell (its price or fee currency); a dividend or tax row's currency is only a guess (often the cash currency), so within a file a trade row's security wins whatever the order, and a later import with a trade corrects a guessed currency (F-020 review). The trade date (`Kauppapäivä`, else `Kirjauspäivä`) is the transaction's day. Signs follow the type, not the file (buys, taxes, fees and withdrawals take cash out; sells take units out and bring cash in), so either sign convention of a Nordnet version reads the same.
  - Types: `OSTO`/`MERKINTÄ` → buy, `MYYNTI`/`LUNASTUS` → sell, `OSINKO` → dividend, `TALLETUS`/`NOSTO` → transfer (cash only), `PALKKIO` and the like → fee; withholding taxes (`ENNAKKOPIDÄTYS`, `LÄHDEVERO`) → fee with the asset (the enum has no tax type, and a tax is a cost of holding), interest → dividend when positive, fee when negative, loan interest → fee. Currency exchanges inside the account (`VALUUTANVAIHTO`) and rows with a cancellation date are skipped and listed as "not recorded"; any other type is a row error, so nothing is guessed silently. The instrument type picks `fund` / `etf`, else `stock`.
  - Accounts: each `Salkku` is a brokerage account (`provider_account_ref` = the portfolio number, EUR, no connection) under a `csv` institution `nordnet`, created on its first import; no account picker, so a re-import lands in the same account. Rows in another cash currency are stored with their own currency (the table has one per row).
  - Dedupe: insert-only with `ON CONFLICT DO NOTHING` on either unique key, Nordnet's `Id` as `provider_txn_ref` and a content hash (`dedupeHash()` over trade date, amount, type, ISIN or symbol, quantity, currency and text). Otherwise identical rows are numbered in Nordnet-id order, not file order (Nordnet lists newest first), since identical rows share a day and so always share an export; a re-export whose ids changed still dedupes by the hash.
  - Holdings: after every import the account's snapshots are deleted and derived again from all its transactions (`deriveHoldings()`: units at the end of each trade day, a buy before a sell on the same day), so an older export imported later corrects them. A running total below zero (the export starts after the buys) is stored as 0 and reported per asset. Assets match by ISIN, else symbol and currency (D-016).
  - Trade prices: each trade's unit price is stored as that day's price (`source` `nordnet_trade`, never replacing an existing row), so holdings without an API price, such as funds the price API does not list, are valued at their last trade. The table shows the price's source and day.
  - Prices: Twelve Data `/eod` (free Basic plan: 8 requests a minute, 800 a day). The client (`price-client.ts`) enforces both limits itself (it waits for a slot and stops at the day's limit), sends the key in the `Authorization` header, adds `mic_code` for Nordic ISINs (FI → XHEL, SE, DK, NO) and treats a 404, an invalid-symbol 400 or a close in another currency as an unknown symbol. Errors come as JSON, often with HTTP 200, so the body decides. `PRICE_API_KEY` is optional (`getEnv()`); without it the job fetches only rates. ECB rates come from `eurofxref-daily.xml` (no key). The worker's `price-update` job runs daily at 07:30 `APP_TIMEZONE`, upserts the rates and one close per security held today (not crypto: F-021), reports unknown symbols, and stops on a limit, key or outage error until the next day.
  - Gain or loss: average cost per account and asset (`costBasis()`: buys add the cash paid including fees, sells remove the average cost of the units sold), shown only when the basis is in EUR and covers the units held. Weight is the share of the valued total.
  - Net worth (before F-022): the dashboard adds each brokerage and crypto account's holdings value today, and 30 days ago with the prices known then, to its cash balance, so the net-worth tile and its change include investments; the account row shows the holdings. The balance history and the allocation stay F-022's.
  - Import UI: the form is on `/investments`, without a preview, because the import is idempotent; the summary lists rows read, inserted, duplicates, not recorded and errors by file line.

## D-021 · Session re-issue on page loads only, so no background response outlives logout (2026-10-24)

- Context: `tests/e2e/auth.spec.ts` "logout clears a day-old session instead of re-issuing it" failed now and then, on `main` too (`--repeat-each=20`: 3 of 20 on `main` at F-022, 4 of 20 plus 3 of 10 on the F-015 branch, whose `/settings` page adds a link). The trace showed why: after the test put a day-old cookie back, the client router prefetched the app shell's links with it; the proxy re-issued the session on each prefetch (D-007 skipped only Server Action calls), and those responses arrived after logout's `Set-Cookie: pf_session=; Expires=1970`, so the browser kept a fresh session. In the app this means logging out can silently leave the browser logged in (only when the session is a day old, i.e. on the first visit of a day). A stateless session cannot be revoked (D-007), and a response cannot be ordered after another, so the fix has to stop the racing responses from carrying a cookie at all. Next 16 strips its own router headers (`rsc`, `next-router-prefetch`) from the request the proxy sees (`proxy.md` → RSC requests), so "skip prefetches" cannot be told from them.
- Decision:
  - The proxy re-issues a day-old session only on a page load: GET or HEAD with `Sec-Fetch-Mode: navigate` and no `Sec-Purpose`/`Purpose: prefetch` (`mayReissueSession()` in `src/lib/auth/routes.ts`, replacing `isServerActionRequest()`). A page load replaces the page, so its response cannot arrive after a logout made from that page. Every fetch a page makes (prefetches, client navigations, `router.refresh()`, Server Actions, a no-JavaScript form POST) keeps the cookie as it is; the session it carries is still accepted.
  - Fetch Metadata headers are sent by every current browser on `127.0.0.1`/`localhost` and HTTPS. A client that sends none never gets a re-issue: its session ends 30 days after login (fail-safe, not fail-open).
  - L3 tests the invariant deterministically at the HTTP level ("only a page load re-issues a day-old session, …": a router-style fetch, a client navigation and a prerender with the old cookie get no `Set-Cookie`, a page load does). Holding a browser request with `page.route` could not stage the race: Chromium attaches cookies when the held request continues. The original logout test stays as the end-to-end check.
- Consequences: the expiry slides with page loads, not with client-side navigation; a tab used only through client navigation for 30 days would be logged out (acceptable for a single-user dashboard that is opened, not kept open for weeks). A page load in another tab at the same moment as a logout can still re-issue (two tabs, same millisecond; accepted, as is D-007's copied-cookie limit). New code that sets the session cookie outside a page load must not assume the proxy refreshes it. A page load still in flight in the same tab when logout is clicked can also re-issue; that is visible (the new page renders logged in), not silent, so it is accepted with the two-tab case. A navigation that does not replace the page (a download link, `window.open`) would reopen the race; there is none today, so add one only with this decision in mind.

## D-024 · Connect-bank flow: hashed single-use state, a connector contract, revoke before remove or archive, the user owns account names (2026-10-24)

- Context: F-007 adds `/connections`, the redirect to the bank and `/connections/callback`. FIN-007 asks for an unguessable, server-stored, single-use `state`, the maximum consent per bank, three error states, naming accounts as checking or savings, "remove = revoke, then delete" and "archive keeps history", with L3 through the fake provider. It leaves open where the state lives and for how long, whether archiving revokes, how the fake plays a bank login, and what happens to a renamed account at the next sync, which until now overwrote the name and type from the provider (D-009).
- Decision:
  - The state is 32 random bytes; only its SHA-256 is stored, in a new table `bank_authorizations` (provider, bank, `expires_at` one hour ahead). The callback deletes the matching row with `RETURNING`, so a state works once even for concurrent callbacks; expired rows are refused and pruned when the next authorisation starts. Results: `invalid_state` (missing, unknown, used, expired), `cancelled` (`error=access_denied`), `provider_error` (another `error`, no code, `completeAuthorization()` failing). The state is consumed in every case, so a cancelled login cannot be retried with the same link.
  - The consent asked for is the bank's `maximum_consent_validity` from `GET /aspsps` (180 days for both banks, FIN-001), less 10 minutes against clock skew; 180 days when the provider gives none.
  - A `BankConnector` contract next to `FinancialProvider` (`types.ts`: `listBanks`, `startAuthorization`, `completeAuthorization`, `revokeSession`; `getBankConnector()`), implemented by Enable Banking (`listBanks()` now returns the normalised `ProviderBank`; new `DELETE /sessions/{id}`) and by the fake, whose stand-in bank page `/connections/fake-bank` approves or cancels back to the callback (404 without `BANK_PROVIDER=fake`).
  - Remove revokes the session, then deletes the connection's accounts (their history cascades) and the connection. Archive revokes too (an archived connection is never synced, so its consent has no use), drops the encrypted session id and archives the accounts; their history stays. A session the provider no longer knows, or one that cannot be decrypted, counts as revoked; any other revoke failure changes nothing.
  - The balance sync no longer overwrites a known account's name and type (only IBAN and currency): they belong to the user once the account exists. New accounts still take the provider's.
  - The callback is a Route Handler that answers `303` with a relative `Location` to `/connections?connected=…` or `?error=…`, so the spent code leaves the address bar and the host behind a proxy does not matter.
  - Compose passes `ENCRYPTION_KEY` and `BANK_PROVIDER` to `app` (and `BANK_PROVIDER` to `worker`).
- Consequences: reconnecting a bank adds a second connection with its own accounts; F-011 (renewal) matches them to the old ones (by uid or IBAN, FIN-001's `identification_hash` note). F-010 triggers the first sync after connecting. Deleting a connection leaves the other leg of a transfer pair one-sided. If the bank's redirect lands after the login session expired, the proxy sends the user to `/login` and the state is lost; connecting again is the remedy. F-013 checks with real banks the redirect's `error` values (only `access_denied` is treated as cancelled) and that `DELETE /sessions/{id}` ends the consent at the bank.

## D-025 · Bank sync: one function under a per-connection try-lock, Sync now per card and for all, a `kind` on sync runs, the first sync inside the callback (2026-10-24)

- Context: F-010 adds the scheduled `bank-sync` job, Sync now on the dashboard and `/connections`, the first sync after connecting, a sync log and the header's last sync. FIN-010 asks for a Postgres advisory lock against two syncs of one connection and a failing connection that neither stops the others nor crashes the worker. It leaves open whether a second sync waits or gives up, what Sync now syncs on each page, how the log tells a connection's two runs per sync apart (D-009/D-010 write one `sync_runs` row for the balances and one for the transactions, with nothing saying which), and whether the first sync blocks the callback.
- Decision:
  - `syncBankConnection()` (`src/server/sync/bank-sync.ts`) is the only entry: balances, then transactions only if the balances succeeded. The lock is `pg_try_advisory_xact_lock(0x4610, first 32 bits of the connection UUID)` held by an idle transaction for the duration of the sync (no session-level lock on a pooled connection, released if the process dies). A second sync is `skipped`, not queued: the running one fetches the same data, and waiting would spend one of the four daily unattended fetches. Two connections sharing the 32 bits would only skip each other's overlapping runs.
  - Remove and archive take the same lock, blocking, in their write transaction (after revoking), so a sync can never restore the accounts of an archived connection or write into a deleted one (a narrow supporting change to F-007's `manage.ts`).
  - `syncBankConnections()` catches a thrown error per connection and returns it as `errorKind: "internal"` (the run is already failed by `failRunOnBug()`); the job logs it with `console.error` and moves on. Retrying "on the next tick" is the schedule itself: no retry queue, no backoff beyond the 6-hour interval.
  - `SYNC_CRON` defaults to `0 */6 * * *` (four a day, PSD2's unattended limit, FIN-001); the env schema only checks 5–6 fields so `src/server/env.ts` does not import node-cron into the Next.js bundle, and the worker fails at start when node-cron rejects the expression.
  - Sync now on the dashboard syncs every active bank connection; on `/connections` each active card has its own button for that connection. Both are Server Actions running the same function in the app process; the message names each connection and the failure kind, never the provider's raw text (that is in the log).
  - `sync_runs.kind` (`balances` / `transactions` / `holdings`, enum `sync_run_kind`, migration `0005_sync_log`) is nullable: rows written before F-010 cannot be classified by a generated migration, and the log shows "—" for them.
  - The callback runs the first sync before it redirects, so the user lands on a page with balances and a log entry. A failure there is in the log and the page says it will be retried; the connection exists either way.
  - The header shows the newest `connections.last_synced_at` of bank connections, set by any succeeded run (a balance run that succeeded before a failed transaction run counts).
- Consequences: Sync now and the first sync count as fetches at the bank; Enable Banking treats a request as PSU-initiated only with the PSU headers, which the client does not send yet, so F-013 must check whether manual syncs eat into the four-a-day limit with real accounts. A long first backfill (Nordea's 540 days) keeps the callback request open until it finishes. The CSV import into a bank-synced account does not take the connection lock (a suggestion from F-012's notes): the unique `(account_id, dedupe_hash)` key and the categorisation lock keep a concurrent import and sync consistent, so it was left out of F-010's scope.

## D-026 · Consent expiry and renewal: skip without a run, a banner above every page, renewal through the pending authorisation, accounts by IBAN then provider id (2026-10-24)

- Context: F-011 asks for a warning banner on every page 14 days before a consent ends and an error banner after it, syncs that skip expired connections and log the skip, and a Renew that runs the authorisation again and attaches the new session to the existing connection and accounts (matched by IBAN, then provider account id) so history continues; status `expired` on expiry or a `ProviderAuthError`. It leaves open where the skip is logged, how the callback knows a login is a renewal, what an id match means when the IBANs differ, what happens to the old session, and which connections can be renewed.
- Decision:
  - The expiry check lives in `syncBankConnection()`, inside the connection's lock: a passed `consent_expires_at` sets an `active` connection `expired`, and an `expired` one is `skipped` (`skipReason: "consent_expired"`) without a provider call. The skip writes no `sync_runs` row (four rows a day per expired connection would bury the log); it is logged by the worker (`console.warn`, every run, because `syncBankConnections()` now includes `expired` connections) and named by Sync now. `skipped` results carry a `skipReason` (`running`, `removed`, `consent_expired`) instead of only a message.
  - The banner is a server component in the app shell above `<main>` (not inside it, and not `role="alert"`, so page-level alerts and landmarks stay unambiguous), reusing the dashboard's `connectionHealth()`: `revoked` and `expired` count as ended too. Each line has Renew; `/connections` cards get Renew in the same window.
  - Renewal reuses the connect flow: `bank_authorizations.connection_id` (nullable, cascade on delete; migration `0006_consent_renewal`) marks a pending renewal, so the state stays the only thing the callback trusts. The callback updates the connection under `lockConnectionSync()`: new encrypted session, `active`, new consent end; a connection archived meanwhile or a session for another bank is refused as `invalid_state` and the new session revoked.
  - Matching (`account-matching.ts`, pure): IBAN first (spaces and case ignored), then the provider account id, but an id match is refused when both IBANs are known and differ; each stored account matches once. Matched accounts keep id, name, type and history and take the new provider id, IBAN and currency (archived ones come back); unmatched session accounts are added; stored ones the session no longer lists are left to the next sync, which archives them.
  - After a renewal the old session is revoked, best effort (an already-ended one is fine, other failures are only logged), so renewing early does not leave two consents running.
  - Only connections of the configured connector can be renewed (the connector must be able to log in to that bank); archived ones cannot (connect again).
- Consequences: the transaction sync's window (7 days before each account's last sync) fetches the expired gap after a renewal as far back as the bank allows; a longer gap than the bank's history leaves a hole. Connecting a bank again instead of renewing still creates a second connection (renewal is the supported path). Real Enable Banking sessions are unverified here: F-013 should check that a renewed Nordea/S-Pankki session's accounts carry the same IBANs (the S-Pankki card has none, so it falls back to the uid, which may change per session and would then add a new card account).
